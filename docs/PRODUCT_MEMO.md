## 1. 目标用户与核心痛点

用户是准备**下一场面试**的本科生：可能是公司实习，也可能是学校或科研**夏令营**；常常一场接一场，去向不一定是公司。

痛点不是「没有题可刷」，而是三个不确定：

- **不知道这场怎么考**：面经散落在牛客、师兄微信和招生简章里，看完仍说不清高频点。
- **不知道自己站不站得住**：简历写了数字和职责，没人按这场要求往下追。
- **不知道下一刀砍哪**：刷完一套通用题，仍不知道该补哪三条。

ChatGPT 能扮演面试官，但不会先聚合这场的情报，也不会在答不出新事实时停下来给出「只补这 3 个」。

## 2. 产品设计说明

一句话：先摸清这场怎么考，再对照简历练；练完只告诉你站住了哪些、还差哪三刀。

主流程五步：这场面试 → 面试情报 → 考情画像 → 针对训练 → 复盘。

核心机制：

- **情报是一等公民**：公开检索、链接抓取、粘贴、上传文件。条数太少或对不上这场，不硬画画像。
- **四类题源**：面经考点、经历已覆盖、经历待核实、要求未覆盖。不是通用题库抽题。
- **追问有终止条件**：最多两轮，只认新增可验证事实；复述、套话、说不清就停。
- **难度分三档**：舒适（做过的部分）、常规（机制再追一层边界）、加压（失败路径与口径）。
- **进度必须真实**：环形覆盖、计时、已验证 / 经不起 / 未覆盖，都来自本场记录，不造假满分。

刻意没做：账号登录、语音视频面试、浏览器插件、完整 HR 面。评委要能打开即用；16 小时内一个闭环比五个半成品重要。

## 3. 版本迭代记录

最初方案是「面经打假 + 考纲自评地图」。做下来发现：学生更急的是**下一场怎么答**，而不是给帖子打假。

于是主路径改成简历 × 选拔要求 × 情报的深挖训练；考纲聚合收成「考情画像」，不再单独占一页让用户自评打钩。

过程中改过的关键点：

- 输入框 `key` 随「有没有内容」变化，导致简历打不了字 → 改为按演示/自有材料分 key。
- 题源写成「情报命中 / 简历风险点」评委和学生都看不懂 → 改为书面四词并附说明。
- 用户不全是公司实习 → 流程词改成这场面试 / 去向 / 方向 / 选拔要求。
- 三档难度提示太弱，出题几乎一样 → 出题与追问都带难度，舒适 / 常规 / 加压角度分开。

## 4. 下一步（若再有一周）

- 把多场复盘做成纵向对比：同一考点隔几天再练，看是站住了还是又被追回来。
- 情报检索按「夏令营 / 实验室 / 公司组」分开权重，减少串岗噪音。
- 反问清单：从面经读出面试官在意什么，生成有信息量的反问，而不是「请问团队氛围如何」。

## 5. AI 工具使用

- **Cursor**：编码、重构、部署脚本、文案迭代；产品取舍与验收由人定。
- **DeepSeek（deepseek-chat）**：出题、追问判定、情报甄别、简历修改建议。判定类调用低温；简历/选拔要求摘录在代码里核验，编造的引用丢弃。
- **公开检索（Tavily / 博查，可选）**：按去向和方向收公开面经。不登录小红书、知乎，不绕过验证码。

代码由 AI 辅助生成，方向、砍功能、上线节奏由人判断。详见提交历史与 `docs/PRD.md`。
